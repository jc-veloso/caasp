# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

TOTVS Protheus ERP integration layer (AdvPL language) for retail client **CAASP**, built for integrator **Artiq**. It exposes REST endpoints (`WSRESTFUL`) that receive NFe/NFC-e (Brazilian fiscal invoice) JSON payloads from CAASP's external systems and drive Protheus's native sales, purchase, return, and store-front engines (`MATA103`, `MATA120`, `MATA010`, `LOJA701`/SIGALOJA) to create matching fiscal documents, financial titles, and product records.

The project is mid-refactor: `api/src/*.prw` is the original, fully synchronous implementation — already deployed and compiled into the client's live Protheus environment/RPO. `api/src/refactoring/` is an in-progress rewrite ("REV2") applied as an **incremental, cumulative patch on top of that same environment**, not a separate, mutually-exclusive deployment. By design, `refactoring/` contains **only files that have actually been modified** for the rewrite — a file untouched by REV2 (e.g. `FATCFOP.PRW`) is deliberately left out of `refactoring/`; its calls (`U_FATCFOP01()`, etc.) resolve fine against the already-deployed top-level original, since both end up compiled into the same RPO over time. Don't "restore" an unmodified file into `refactoring/` just because some `refactoring/` source calls into it and no local copy exists there — that absence is usually intentional, not a bug (see the file-integrity note below for how this was learned the hard way). See "Architecture" below before assuming either directory is the sole source of truth for a given endpoint.

Business driver (from `api/src/docs/transcrição_reunião_caasp.txt`): production reports of severe slowness during high-volume product registration (pharmacy/bookstore items registered constantly). Rollout is phased — NFC-e first (higher volume, fewer products/note, easier test bed), then NFe, reusing the same validated rules engine for purchase/return/transfer.

`api/src/docs/Modelagem_TabelasMuro_CAASP_Rev2.docx` is the schema doc for the `ZZA`-`ZZF` staging tables described below — it's a OneDrive placeholder in this checkout (not synced locally), so it may need to be opened directly in OneDrive/Word rather than read as a file.

## Working in this codebase

**Scope restriction: only modify files under `api/src/refactoring/`.** The top-level `api/src/*.prw` originals and everything under `fin/` are off-limits — do not edit, refactor, or "fix" them even if they contain the same bug as their `refactoring/` counterpart. Treat the top-level files as read-only reference for understanding what the refactor is replacing.

There is no conventional build/lint/test tooling (no npm/make/CI). Development happens entirely through TOTVS Developer Studio's VS Code extension:

- Compiling and running requires a live Protheus application server; `.vscode/launch.json` configures the `totvs_language_debug` debugger against `../totvs/bin/smartclient/smartclient.exe`. There's no way to compile or execute AdvPL standalone from the shell.
- **`api/src/refactoring/` is split into three subfolders** (reorganized 08/2026 — José Carlos): `process/` (shared engines: `FATPI01U/E/S/D.prw`), `endpoints/` (REST `WSRESTFUL` sources: `FATPI01_V2/02_V2/08_V2/09/10.prw`), `jobs/` (scheduled `FATZZ*` sources: `FATZZ901.prw`, `FATZZA01.prw`...`FATZZF01.prw`). This is a pure physical reorganization — no file content changed as part of the move (verified file-by-file against git history). All filenames below are given bare (e.g. `FATPI01S.prw`); see the file tables further down for which subfolder each lives in.
- **Compile order is manual and load-bearing** — AdvPL has no package manager or dependency graph, and later files in a compile batch can silently fail to resolve `User Function`s defined in files compiled after them. Respect the order documented in file headers (the subfolder split above doesn't change this ordering — it's still governed by these cross-file `U_` calls, not by directory layout; **TDS's own batch/patch-generation behavior across the three subfolders hasn't been re-verified since the reorg, worth confirming it still honors this order rather than e.g. compiling alphabetically per-folder**):
  - `FATPI01U` → `FATPI01E` → `FATPI01S` → `FATPI01D` → `FATPI01_V2` (utility functions must compile before the engines that use them; first four live in `process/`, last one in `endpoints/`)
  - `FATZZF01` (in `jobs/`) must compile before the other `FATZZA01`...`FATZZE01` job files (also `jobs/`) — it defines the shared `U_UPDSTAT`/`U_ZZCALLBK`/`U_ZZF_GRV`/`U_BUSCACAD` functions they (and `FATPI10.prw`, in `endpoints/`) all call.
  - `FATPI01E.prw` and `FATPI01S.prw` (`process/`) must also compile before `FATZZA01.prw`/`FATZZB01.prw`/`FATZZC01.prw`/`FATZZD01.prw` (`jobs/`) — those jobs call `U_JSON_COMPRA`/`U_PI_GER_E2` (defined in `FATPI01E.prw`), `U_PI_ROLLBACK_NF` (defined in `FATPI01S.prw`), and — since 08/2026, `FATZZD01.prw` too — `U_PI_SAIDA_X` (defined in `FATPI01S.prw`). See "NFe engine execution" below for why these had to be promoted to `User Function` in the first place.
  - `FATZZF01.prw` must compile before `FATZZ901.prw` (both `jobs/`) — it calls `U_ZZX_Gravar`/`U_UPDSTAT`/`U_BUSCACAD` (defined in `FATZZF01.prw`). `FATZZ901.prw` also calls `U_FATCFOP01()` — that's defined in the top-level `api/src/FATCFOP.PRW`, already compiled into the live environment; there's no `refactoring/` copy to sequence against, since `FATCFOP.PRW` was never modified for REV2 (see the file-integrity note below).
- AdvPL only resolves the **first 10 characters** of a function name for cross-file symbol matching. This has caused real collisions in this codebase (e.g. the old `U_FZ_PROS_LOJA` collided with `U_FZ_PROS_X`, later renamed `U_FZ_LOJA_X`, itself since renamed to `U_PI_LOJA_X` — see naming convention below) — keep new `U_`-prefixed function names distinguishable within 10 characters, or verify uniqueness before naming one. Before adding any new `User Function` to `api/src/refactoring/`, check its 10-char `U_` signature against every existing `User Function` in the whole project (not just `refactoring/`) — `refactoring/` patches compile cumulatively into the same live RPO as the top-level originals, so a new name really can collide with one already resident there, not just a hypothetical.
- **Naming convention**: shared helper/engine functions in `api/src/refactoring/` use the `PI_` prefix (e.g. `U_PI_STR_X`, `U_PI_SAIDA_X`), renamed from the original `FZ_` prefix because `FZ_` collided with unrelated legacy sources already compiled in the client's environment. The top-level `api/src/*.prw` originals still use `FZ_` — that's expected and must not be changed (see scope restriction above). Any new function added to `refactoring/` should follow `PI_`, not `FZ_`.
- **`WSRESTFUL` resource names must not be reused across generations.** This is a separate, full-name collision distinct from the 10-char `User Function` truncation issue above: `WSRESTFUL <name>` declares a REST resource, and the top-level originals (`FATPI01.prw`, `FATPI02.prw`, `FATPI08.PRW`) are already compiled in the client's environment under their bare names (`FATPI01`, `FATPI02`, `FATPI08`). Every `refactoring/` endpoint therefore declares its own resource under a `_V2` (or similarly distinct) suffix — `WSRESTFUL FATPI01_V2`, `FATPI02_V2`, `FATPI08_V2`, `FATPI09_V2` — and the `WSMETHOD ... WSSERVICE <name>` implementation must reference that same suffixed name, not the bare original. Keep this pairing consistent when adding or editing any `WSRESTFUL`/`WSMETHOD` block in `refactoring/`.
- `.ptm` files (auto-named `api/src/refactoring/customDD-MM-YYYY-HH-MM-SS.ptm` by TDS on each "Generate Patch", plus `fin/patch/F150SUM.ptm`) are binary TOTVS deployment patches — opaque build output, never a source of truth or something to hand-edit, and gitignored. The `.prw` files are canonical.
- Never read the `_JSON` memo/CLOB field of any `ZZ*` staging table through a TOPCONN/SQL query alias — always reopen the native table area and `DbGoto(nRecno)` first. Multiple `[FIX-MEMO]` comments across the job files exist because this was a real silent-truncation bug; any new code touching these tables must follow the same pattern.
- **A `refactoring/` source calling into a function with no local definition in `refactoring/` is not automatically a bug — check the top-level original before "fixing" anything.** `refactoring/` intentionally holds only files actually modified for REV2; an unmodified dependency (e.g. `FATCFOP.PRW`, called via `U_FATCFOP01()` from `FATPI01S.prw`/`FATZZD01.prw`/`FATZZ901.prw`) is deliberately left out, because the top-level original is already compiled into the live environment and resolves the call fine — duplicating it into `refactoring/` would be redundant at best and a genuine redefinition collision at worst, since both compile cumulatively into the same RPO. (Learned this the hard way in 08/2026: `FATCFOP.PRW` was mistakenly copied into `refactoring/` on the assumption its absence was accidental data loss, then reverted once the actual policy — refactoring/ mirrors only the delta — was clarified.) `FATPI03.PRW` is a genuine example of this pattern today: no `refactoring/` copy exists, `refactoring/` sources needing supplier-upsert behavior would call into the top-level original.
- **Never call `RpcSetEnv`/`RpcClearEnv` inside a `WSRESTFUL` endpoint.** Confirmed against official TOTVS TDN ("Abertura de ambiente em Web Service", from version 12.1.27): the environment is already prepared automatically by `PREPAREIN` in `appserver.ini`, with company/branch resolved from the request's `TenantId` header. Calling `RpcSetEnv` again inside the endpoint conflicts with that already-open environment — this was a confirmed, reproduced bug (first found and fixed in `FATPI09.prw`, then replicated across `FATPI01_V2.prw`, `FATPI02_V2.prw` — which never had the pattern —, `FATPI08_V2.prw`, `FATPI10.prw`). **This rule is endpoint-only** — the 6 scheduled jobs (`FATZZA01.prw`...`FATZZF01.prw`) still need `RpcSetEnv`/`RpcClearEnv` as before, since they run via Schedule with no `PREPAREIN` and start with no environment at all. Don't "fix" the jobs to match the endpoints.

## Architecture

### Original implementation and the REV2 patch layer

**`api/src/*.prw`** — original, synchronous implementation, already deployed and compiled in the client's live environment. Each REST endpoint does everything inline (payload parse → company/CFOP routing → fiscal engine call via `MSExecAuto`/`ExecAuto` → financial posting) before returning the HTTP response:
- `FATPI01.prw` — `POST /fatpi01`, the original monolith (3171 lines): handles both NFe and NFC-e (`cod_Mod` 55/65) in one function.
- `FATPI02.prw` — `POST /fatpi02`, product (SB1) upsert via `MATA010`.
- `FATPI03.PRW` — `POST /fatpi03`, supplier (SA2) upsert via `MATA020` (MVC/`FwLoadModel`).
- `FATPI06.prw` — `POST /fatpi06`, customer (SA1) import (MVC).
- `FATPI07.PRW` — `POST /fatpi07`, original standalone NFC-e (modelo 65) endpoint.
- `FATPI08.PRW` — `POST /fatpi08`, "Hub de Vendas - SIGALOJA" sales-receipt endpoint; core motor `U_FATPI0801`.

**`api/src/refactoring/*.prw`** — REV2 patch: REST endpoints now only validate/classify the payload and write a row to a `ZZ*` staging table; separate scheduled `User Function FATZZ*01()` jobs poll their table and invoke the actual fiscal engine asynchronously, then POST a callback to the iPaaS on completion. This directly targets the synchronous product-registration slowness reported by the client, though note the underlying per-row `MsExecAuto(MATA010)` cost is unchanged — only its timing moved off the HTTP path. Contains **only the files REV2 actually changed** — see the note above about not assuming an absent file is a bug. Split into three subfolders (see note above); tables below are grouped the same way.

**`process/`** — shared engines, called by both endpoints (synchronously, pre-08/2026) and jobs (now):

| File | Responsibility |
|---|---|
| `FATPI01U.prw` | Shared helpers: safe JSON extraction (`U_PI_STR_X`/`U_PI_VAL_X`), CNPJ cleanup, date parsing, `SM0` company/branch lookup by CNPJ (`U_PI_FILIAL_X`), CFOP inversion (`U_PI_INVCFOP`), `ExecAuto` error logging (`U_PI_LOG_X`), branch lookup by CNPJ for transfer/CONVENIOS flows (`U_FATPIEMP` — promoted from `Static Function FATPIEMP`, same cross-compile-batch reason as `U_PI_ROLLBACK_NF`/`ZZX_Gravar`: called from `FATPI01S.prw`, `FATPI01D.prw`, `FATPI01E.prw`). Compiles first. |
| `FATPI01E.prw` | Purchase engine ("Motor de Entrada"): `U_PI_GERAPC_X` (MATA120), `U_PI_GERANF_X` (MATA103 classify). |
| `FATPI01S.prw` | Sales engine ("Motor de Saida"): `U_PI_SAIDA_X` (MaNfs2Nfs direct billing — used by both `FATZZA01.prw`, NFe Saida, and, since 08/2026, `FATZZD01.prw`, NFCe), `U_PI_LOJA_X` (NFCe quote via LOJA701/SIGALOJA — orphaned since 08/2026, no caller left in `refactoring/`; `FATZZD01.prw` moved to `U_PI_SAIDA_X` instead, see "Known open issues" below. Left defined here, not removed), `FATPI0101`/`U_FATPI01NF` (transfer auto-entry, CONVENIOS), `U_PI_ROLLBACK_NF` (sales reversal on CONVENIOS failure — promoted from `Static` to `User Function` so `FATZZA01.prw` can call it). |
| `FATPI01D.prw` | Return engine ("Motor de Devolucao"): `U_PI_DEVOL_X` (MATA103 type D/N). |

**`endpoints/`** — `WSRESTFUL` REST sources, all thin (validate/classify/enqueue only, no engine calls since the async migration):

| File | Responsibility |
|---|---|
| `FATPI01_V2.prw` | `POST /fatpi01/v2` — thin orchestrator, **NFe modelo 55 only** (rejects modelo 65). Validates payload, resolves branch by CNPJ, extracts `cod_ChaveNFe`, checks duplicity against `ZZ9`, and **only enqueues the raw payload into `ZZ9`** — no CFOP/`cOper` classification, no numbering, no engine call happens here anymore. See "NFe pre-classification (`ZZ9`)" below. |
| `FATPI02_V2.prw` | `POST /fatpi02/v2` — thin wrapper; logic moved into `U_PI_PROD_X` so the async job can call it directly. |
| `FATPI08_V2.prw` | `POST /fatpi08/v2` — validates/dedupes/enqueues into `ZZE` instead of processing inline; unchanged core motor `U_FATPI0801` now called by the job. |
| `FATPI09.prw` | `POST /fatpi09/v2` — new dedicated NFC-e endpoint, extracted from the old `cModDoc=="65"` branch; enqueues into `ZZD`. No longer checks SB1 itself — see `prod_Pendente` below. Has a known open risk — see below. |
| `FATPI10.prw` | `POST /fatpi10/v2` — pending-product intake: the iPaaS calls this with `{tipo, chave, cod_Produto[]}` when it detects a note is missing products. Resolves the parent row by `chave` (searches `ZZ9` first, then `ZZA`/`ZZB`/`ZZC`, for `tipo="NFE"` since the iPaaS doesn't distinguish Saida/Devolucao/Entrada — `ZZ9` is the common case, a new NFe note usually hasn't been classified yet when the pending-product notice arrives; `ZZD` for `"NFC"`; `ZZE` for `"RCV"`) just to classify `ZZF_TIPONF` and flip `_PRDPEN`, then writes one `ZZF` row per pending code via `U_ZZF_GRV`. Carries no product detail — `FATZZF01.prw`'s `ZZF_CADPRD` fetches the authoritative record from the external CAASP API at processing time (see below). |

**`jobs/`** — scheduled `User Function FATZZ*` sources, one per `ZZ*` staging table plus the `ZZ9` classifier:

| File | Responsibility |
|---|---|
| `FATZZ901.prw` | Scheduled job for `ZZ9` — reads rows with `ZZ9_STATUS IN ('P','A') AND ZZ9_PRDPEN='N'`, runs the full classification that used to live in `FATPI01_V2.prw` (SA1/SA2 routing, `cOper` S/D/E, numbering, duplicate check against SF1/SF2, product/CFOP/TES loop, `oHead` synthetic-field enrichment), and writes the classified result into `ZZA`/`ZZB`/`ZZC` via `U_ZZX_Gravar`. See "NFe pre-classification (`ZZ9`)" below. |
| `FATZZA01.prw`...`FATZZF01.prw` | Scheduled jobs, one per `ZZ*` table — see table below. `FATZZF01.prw` also defines the shared `U_UPDSTAT`/`U_ZZCALLBK`/`U_ZZF_GRV`/`U_ZZX_Gravar`/`U_BUSCACAD` used by all of them (and by `FATPI10.prw`, `FATPI01_V2.prw`, `FATZZ901.prw`). |

`FATCFOP.PRW` (`ValidaCFOP` class, CFOP validation/exception rules; `ProcessaRegras()` is an extension point for CFOP-specific overrides) has **no `refactoring/` copy** — untouched by REV2, `FATPI01S.prw`/`FATZZD01.prw`/`FATZZ901.prw` call `U_FATCFOP01()` straight into the top-level original (see the note above). `FATPI06.prw` and `FATPI03.PRW` are the same situation — no `refactoring/` copy, calls resolve against the top-level originals. (`FATPI06.prw` used to exist as an identical, unmodified copy under `refactoring/` — that copy is gone as of the 08/2026 subfolder reorg; not a REV2 change, just cleanup of a stray duplicate that was never actually diverging from the top-level original.)

### Async staging ("Muro") tables

Custom `ZZ*` tables buffer REST input for job pickup. Each row carries `_STATUS` (`P` pending, `A` in-progress, `S` success, `E` error), `_JSON` (raw payload memo — see memo-read rule above), and `_ERRMSG`.

| Table | Domain | Job | Engine called |
|---|---|---|---|
| `ZZA` | NFe Saida (sales exit) | `FATZZA01` | `U_PI_SAIDA_X` |
| `ZZB` | NFe Devolucao (return) | `FATZZB01` | `U_PI_DEVOL_X` |
| `ZZC` | NFe Entrada (purchase) | `FATZZC01` | `U_PI_GERAPC_X` + `U_PI_GERANF_X` |
| `ZZD` | NFCe (modelo 65) | `FATZZD01` | `U_PI_SAIDA_X` (Faturamento — see "Known open issues" below; was `U_PI_LOJA_X`/`LOJA701`/SIGALOJA until 08/2026) |
| `ZZE` | Recibo de Venda (sales receipt) | `FATZZE01` | `U_FATPI0801` |
| `ZZF` | Pending-product queue (blocks any note on missing SB1 product) | `FATZZF01` | `U_PI_PROD_X` |

Each `FATZZ*01.prw`/`FATZZ901.prw` job bootstraps its own environment via a file-top `CEMPPAD`/`CFILPAD` pair passed to the initial `RpcSetEnv` (before `SuperGetMv`/`cEmpAnt` exist to look it up any other way). All six jobs (`FATZZ901`, `FATZZA01`...`FATZZE01`) declare it as `Static CEMPPAD := "01"` / `Static CFILPAD := "01001"` (CAASP's real company/branch — confirmed 08/2026; an earlier `#Define CEMPPAD "99"` / `#Define CFILPAD "01"` placeholder had every job bootstrapping into the wrong branch, so each job's main query — filtered by `xFilial(cTabMuro)` right after that `RpcSetEnv` — silently matched zero rows against records written by the endpoints under the real branch; no error, just a queue that never drains). `FATZZF01.prw` is the deliberate exception: it still has the old `STATIC CEMPPAD "01"` / `STATIC CFILPAD "01001"` syntax (missing the `:=`, likely a compile-breaking typo) — left alone on purpose, that file's fix is owned separately.

`ZZX_Gravar` (writes a staging row to `ZZA`-`ZZE`, and now `ZZ9`) is currently duplicated as a local `Static Function` in `FATPI08_V2.prw` and `FATPI09.prw` rather than shared — each has a comment flagging it for future consolidation; don't be surprised the same helper appears there too. The `FATPI01_V2.prw` copy was different: it got **promoted to a shared `User Function`** in `FATZZF01.prw` (08/2026) because `FATZZ901.prw`, a separate compile-order family, needed to call it too — same pattern already used for `U_ZZF_GRV`. It also gained a defensive `FieldPos(cTabMuro + "_PROC") > 0` guard before writing `_PROC`, because `ZZ9` — unlike `ZZA`-`ZZE` — has no `_PROC` field; pass `cProc := ""` when writing to `ZZ9`, the value is simply skipped. Prefer this promote-to-`FATZZF01.prw` pattern over adding more local copies if another cross-compile-family caller needs `ZZX_Gravar`.

Same pattern applied to `BuscaCad` (validates CEST against `F0G`/NCM against `SYD`) — promoted to `User Function BUSCACAD` in `FATZZF01.prw` (08/2026, alongside the NFC-e motor swap below) because both `FATZZD01.prw` and `FATZZ901.prw` need it in their product/CFOP loop and neither could see the original `Static Function BuscaCad` in `FATPI01U.prw` (different compile batch). Unlike `ZZX_Gravar`, the original `Static Function` was left in place in `FATPI01U.prw` rather than removed — cleanup of that copy is deliberately left open, Antonio's call since he owns edits to that file.

### NFe engine execution: async-only, no double-run

**Superseded entry point**: as of the `ZZ9` migration (see below, also 08/2026), nothing writes into `ZZA`/`ZZB`/`ZZC` directly from an HTTP endpoint anymore — `FATZZ901.prw` is now the only writer, having taken over the classification role described in this section from `FATPI01_V2.prw`. The bug narrative and fix below are unchanged and still accurate for how `FATZZA01.prw`/`FATZZB01.prw`/`FATZZC01.prw` consume `ZZA`/`ZZB`/`ZZC` — just mentally substitute "`FATZZ901.prw`" wherever this section says `FATPI01_V2.prw` did the enqueuing.

`ZZA`/`ZZB`/`ZZC` (the NFe domain) had a real bug until fixed in 08/2026: `FATPI01_V2.prw` ran the fiscal engine (`U_PI_SAIDA_X`/`U_PI_DEVOL_X`/`U_PI_GERAPC_X`+`U_PI_GERANF_X`) **synchronously inside the endpoint**, and only wrote to the `ZZ*` queue *after* the engine already succeeded — the queue was an audit trail of finished work, not a work queue. But `FATZZA01.prw`/`FATZZB01.prw`/`FATZZC01.prw` **also** independently call the same engines, reading parameters (`cCod`, `cLoja`, `cNF`, `cSer`, `cLeg`, `cFil`, `cTab`, ...) from synthetic `_COD`/`_LOJA`/`_NF`/... keys on `oHead` that `FATPI01_V2.prw` never wrote anywhere — confirmed via `U_PI_STR_X`, which returns `""` for a missing key. The jobs had been running (or trying to) with empty parameters since they were written; never caught because the full flow had never been exercised end-to-end.

Fixed by making `FATPI01_V2.prw` genuinely async, matching every other endpoint in this codebase:
1. It still does all fiscal routing/numbering/CFOP resolution synchronously (sections 1-6 — SA1/SA2 counterpart routing, `cOper` S/D/E determination, NF numbering, duplicate check against SF1/SF2, per-item SB1/NCM/CEST/CFOP/TES loop). None of that changed.
2. Before enqueueing, it writes the resolved values onto `oHead` as synthetic fields (`_COD`, `_LOJA`, `_NF`, `_SER`, `_LEG`, `_FIL`, `_TAB`, `_TRANSF`, `_COND`, `_CNPJEMIT`, `_CNPJDEST`) so the job can reconstruct the engine call on its own.
3. It enqueues into `ZZA`/`ZZB`/`ZZC` **without calling any engine** — no `U_PI_SETFCA`, no `U_PI_SAIDA_X`/`U_PI_DEVOL_X`/`U_PI_GERAPC_X`/`U_PI_GERANF_X`, no `JSON_COMPRA`/`PI_GER_E2`, no CONVENIOS transfer logic. All of that now lives only in the jobs (`ZZA_MotorSaida`/`ZZB_MotorDevolucao`/`ZZC_MotorEntrada`), which already expected to own this — `U_JSON_COMPRA`/`U_PI_GER_E2` were already being called from `FATZZB01.prw`/`FATZZC01.prw` before this fix (promoted to `User Function` in `FATPI01E.prw` for exactly this reason). `FATZZA01.prw` didn't yet have the CONVENIOS (transfer-between-branches) + rollback step, so that part was added new, calling `U_PI_ROLLBACK_NF` (promoted from `Static Function FZ_ROLLBACK_NF` in `FATPI01S.prw` for the same cross-compile-batch reason).

**Why the old jobs' bug went undetected**: `FATPI01_V2.prw` and the `FATZZ*01.prw` jobs are compiled/patched as separate batches (`FATPI01U>E>S>D>_V2` vs `FATZZF01` then `FATZZA01...FATZZE01`) — even though both ultimately land in the same cumulative RPO, a `Static Function` declared in a file from one batch is invisible to code compiled in a different batch, since `Static Function` visibility is scoped to the specific compile operation, not the whole environment. Anything a job needs to call that lives in the `FATPI01*` batch must be a `User Function`, called with `U_`. This is the same reason `ZZX_Gravar`/`U_ZZF_GRV` need the `U_` + promotion treatment described above — don't assume a function is reachable from a job just because it's reachable from the endpoint that used to call it inline, or because both are technically in the same live environment.

### Pending-product flow (`prod_Pendente`)

Detecting a missing `SB1` product used to happen inside the ingestion endpoints (each did its own `SB1` lookup per item). That responsibility moved to the iPaaS:
1. **Ingestion** (`FATPI01_V2.prw`, `FATPI08_V2.prw`, `FATPI09.prw`): reads a `prod_Pendente` field (`"S"`/`"N"`) sent at the root of the payload and writes it straight through to `<TAB>_PRDPEN` via `ZZX_Gravar` — no local `SB1` check anymore. `FATPI01_V2.prw` writes to `ZZ9_PRDPEN` (not `ZZA`/`ZZB`/`ZZC` — that target doesn't exist yet at ingestion time).
2. **Pending-product intake** (`FATPI10.prw`): when the iPaaS's own check finds missing products for a note, it calls `POST /fatpi10/v2` separately with `{tipo, chave, cod_Produto[]}` — codes only, no product detail. It just resolves which parent `ZZ*` row the `chave` belongs to (to classify `ZZF_TIPONF` and flip `_PRDPEN`) and enqueues one row per pending code into `ZZF` via `U_ZZF_GRV`.
3. **Resolution** (`FATZZF01.prw` → `ZZF_CADPRD`): polls `ZZF`, and for each pending row **calls an external CAASP API** (`GET https://api.caasp.org.br/integracoes/totvs/produtos/listar?int_PaginaAtual=1&int_ItemsPorPagina=1&cod_Produto=<codigo>`, `Authorization: Bearer <token>`) to fetch the authoritative product record, then calls `U_PI_PROD_X` with it directly — the response's field names (`cod`, `descricao`, `tipo_Produto`, `grupo`, `pos_IPI_NCM`, `preco_Venda`, `des_ProdutoCEST`, `cod_ProdutoEAN`, `cod_ContaContabil`, `origem`, `unidade`, `armazem`, `peso`) already match what `U_PI_PROD_X` expects, so no field-name mapping is needed (replaced the old, uncertain fiscal-item→product mapping). Once all codes for a `ZZF_CHVREF` are resolved, flips the parent's `_PRDPEN` back to `'N'` and releases the note.
   - **Requires the `MV_XCPTOK` config parameter** (Bearer token for the CAASP API) to be set in the target environment — `ZZF_CADPRD` fails fast with a clear error if it's empty.
   - The GET call uses the native `HttpGet(<cUrl>,[cGetParms],[nTimeOut],[aHeadStr],[@cHeaderGet])` function — **not** `FWHTTPClient`. That class was tried first and confirmed non-functional in this Protheus build: neither `:AddHeader` nor `:SetHeader` exist at runtime (both tested live, both failed with "Cannot find method"). Every `FWHTTPClient` call site in `refactoring/` (`ZZF_CADPRD`'s GET, and the iPaaS callback's POST — `CBackNotaF`/`CBackRecib` at the time, since unified into `CBackIpaas`, see below — all in `FATZZF01.prw`) was converted to `HttpGet`/`HttpPost`; a project-wide grep confirms no `.prw`/`.PRW` file (top-level included) still references the class. POST call sites use `HttpPost(<cUrl>,[cGetParms],[cPostParms],[nTimeOut],[aHeadStr],[@cHeaderGet])` — the 2nd param is `cGetParms` (query string), **not** content-type; `Content-Type: application/json` goes in the `aHeadStr` array instead. Headers are passed as an array of `"Nome: Valor"` strings (e.g. `aAdd(aHeader, "Authorization: Bearer " + cToken)`). Neither function returns a numeric status code — success is inferred from the `cHeadRet` output-by-reference parameter via substring check (`"200" $ cHeadRet .Or. "201" $ cHeadRet .Or. ...`); good enough for now, a stricter version would parse the response's first line (`"HTTP/1.1 200 OK"`) instead.
   - The test token observed continued working ~8h after issue despite a 1-hour `exp` claim — `exp` may not be enforced server-side. If the API starts returning 401s, `MV_XCPTOK` needs a fresh token.

`FATPI10.prw` doesn't verify the caller's classification — for `tipo="NFE"` it searches `ZZ9` first, then `ZZA`/`ZZB`/`ZZC` (all three, plus `ZZ9`, are modelo 55 or pre-classification; the iPaaS payload doesn't say which) rather than trusting a single guessed mapping. When found in `ZZ9`, `ZZF_TIPONF` is set to `"ZZ9"` (not `"NFS"`/`"NFD"`/`"NFE"`) — `FATZZF01.prw`'s release routing (both the success path and the `[NOTIFICA-FALHA]` failure path) has a `Case cTipoNF == "ZZ9" ; cTabPai := "ZZ9"` branch for this; `ZZF_LIBNF` needed no change since its field-name construction (`cTabPai + "_CHVNFE"` / `cTabPai + "_PRDPEN"`) already works generically for `"ZZ9"`.

### `ZZ9` — NFe pre-classification table

`ZZ9` is an intermediary staging table, exclusive to the NFe domain (`ZZA`/`ZZB`/`ZZC`) — NFCe (`ZZD`) and Recibo (`ZZE`) don't need it, they already classify unambiguously on their own. It exists because `FATPI10.prw`'s pending-product payload carries no CFOP, so a note can no longer be classified into `ZZA`/`ZZB`/`ZZC` directly at the ingestion endpoint — classification has to wait until pending products (if any) are confirmed resolved. `ZZ9` is where every NFe note lands first (pending products or not), written by `FATPI01_V2.prw`; `FATZZ901.prw` (job) reads it, classifies, and writes the result into `ZZA`/`ZZB`/`ZZC`. See `FATPI01_V2.prw`/`FATZZ901.prw` in the file table above, and "NFe engine execution" above for the fuller history.

Named `ZZ9` rather than `ZZG` — a deliberate choice (José Carlos) so it sorts before `ZZA` numerically/alphabetically, reflecting that it's the earlier stage in the flow.

`FATZZ901.prw`'s main loop guards against two cross-iteration state leaks that are easy to reintroduce if this function gets touched again:
- **`ZZ9_DESTMU` filial capture**: `ZZ901_Classifica` may call `RpcClearEnv`/`RpcSetEnv` mid-classification to switch to the branch resolved from the note's CNPJ. The loop captures `ZZ9_FILIAL` from the query row (`cFilOri`) *before* calling `ZZ901_Classifica`, and uses that captured value — not `xFilial("ZZ9")` — in the `ZZ9_DESTMU` UPDATE afterward. Evaluating `xFilial("ZZ9")` after the call would silently match zero rows for any note that forces a branch switch, since the environment has already moved on from the branch the row was read under.
- **`dDataBase` reset per note**: `ZZ901_Classifica` sets `dDataBase := dVencto` only when the note's `dVencto` is non-empty (inherited from the original synchronous endpoint, where each HTTP request was an isolated process). In the job, several notes run in the same process — if a note has an empty `dVencto`, `dDataBase` would otherwise keep the previous note's value. The loop captures the real system `dDataBase` once, right after `RpcSetEnv` (`dDataBaseSis`), and resets `dDataBase := dDataBaseSis` at the start of every iteration before calling `ZZ901_Classifica`.

## Known open issues (check before touching related code)

- **NFC-e tax recalculation risk — accepted, not resolved**: `FATZZD01.prw`'s motor was `U_PI_LOJA_X` (`LOJA701`/SIGALOJA, writes `SL1`) until 08/2026, kept specifically to avoid this risk (see the file's `[FIX-MOTOR]` history). That decision was revisited after reviewing the pre-refactor monolith (`FATPI01__2_.prw`), which showed NFCe belongs in the Faturamento engine (`SF2`/`SD2`, `F2_ESPECIE`/`F3_ESPECIE := "NFCE"`) just like NFe, not in SIGALOJA — `FATZZD01.prw` now calls `U_PI_SAIDA_X` (same engine `FATZZA01.prw` uses for NFe Saida). The underlying risk — `MaNfs2Nfs` recalculates taxes via TES/CFOP at inclusion time, but NFC-e was already authorized by SEFAZ with PDV-calculated values — **still exists**; the engine swap didn't fix it, it just means NFCe now shares the same trade-off NFe already carries in production. The old `FATPI08`/`U_FATPI0801` path (still used by `ZZE`/Recibo) remains the only motor that writes without recalculating.
- **`FATPI09.prw` unverified assumptions**: NFCe JSON total-value field names copied from the Recibo pattern (unconfirmed); `L4_FORMA` (payment method) stores raw JSON text with no DE-PARA mapping to internal codes; `LQ_TIPOCLI` is hardcoded `"F"` (pessoa física) — no PJ scenario handled.
- **`ZZE` (Recibo) callback unified with Notas Fiscais (08/2026)**: `CBackNotaF`/`CBackRecib` merged into a single `CBackIpaas` in `FATZZF01.prw`, dispatched by `ZZCALLBK` based on `cTab` — same payload shape (`cod_Subseccao`/`des_Processamento`/`flg_Processamento`) for both domains per Arthur's specs ("Notas Fiscais (01)" and "Recibos de Venda (08)"), only the target URL, the key field name (`cod_ChaveNFe` vs `num_PedidoReciboVenda`), and the success-message prefix ("Nota" vs "Nota Varejo Processada") differ. The old generic `MV_XIPURL` + `/protheus/callback` mechanism is gone. `num_PedidoReciboVenda` is populated with the same reference code already flowing through `ZZE_CODRCB` (the `chave`/`cod_ReciboVenda` value the iPaaS sent at ingestion, already in `"ODT_..."` shape) — not a new number generated by the motor.
- **`ZZA_TRANSF` field — abandoned (08/2026, José Carlos)**: referenced in `FATZZ901.prw`/`FATZZA01.prw` code (`oHead['_TRANSF']`, `U_ZZX_Gravar(..., "TRANSF", ...)`) but the SIGACFG dictionary field was never pursued to deployment — decided not to chase it further, deliberately left as-is. Note `U_ZZX_Gravar`'s `cCampoExtra`/`cValorExtra` write (`FieldPut(FieldPos(...), ...)`) has no `FieldPos > 0` guard here (unlike the `_QTPROD` write added later), so this hasn't been verified safe if the field is truly absent from the dictionary in a given environment — untested, not confirmed harmless. Don't "fix" this by chasing the SIGACFG field again absent new instruction; if it ever surfaces as a real error, that's the trigger to revisit.
- **`U_PI_SAIDA_X` blank `D2_FILIAL` — fixed 08/2026, root-caused against a real failure**: `nD2FILIAL` (the `D2_FILIAL` position in `aStruSD2`) was computed via `Ascan` but never actually used to populate `aItens` — unlike `nF2FILIAL`, which correctly fills `aCabs[nF2FILIAL] := xFilial("SF2")` in the header. Every item `U_PI_SAIDA_X` ever generated had a blank `D2_FILIAL` (the item-array init loop only clears character fields to `""`). This affects both `FATZZA01.prw` (NFe Saida) and `FATZZD01.prw` (NFCe), since both call `U_PI_SAIDA_X`. Root-caused against a real test failure: 1 of 20 NFCe broke — decoding the failing note's access key and the one processed immediately before it showed the failing note's CNPJ resolved to filial `01009` while the prior note's CNPJ resolved to `01071`. `U_PI_SAIDA_X` detects `aEmpFil != cEmpAnt/cFilAnt` mid-function and switches branch via `RpcClearEnv`/`RpcSetEnv` — with `D2_FILIAL` blank, whatever implicit fallback the note relied on apparently carried over stale state from the branch processed immediately before it, only surfacing when two different branches land back-to-back in the same Job run (which is why 19/20 same-branch notes in the test passed and only the one at the branch boundary broke). Fixed by explicitly setting `aItens[nPos, nD2FILIAL] := xFilial("SD2")` at item-build time, evaluated after any mid-function branch switch — no longer depends on any implicit default.
